# Personal AI OS — Independent Audit, 2026-11-08

Auditor: external review, read-only.
Scope: repository at `personal-ai-os/` (branch `main`, HEAD `6f2770e`), deployed Worker
`https://personal-ai-os.jatin-personal-ai.workers.dev`, remote D1 `personal-ai-os-db`
(`3f9305ea-cc7b-47bc-ac11-07faff106096`). No code, config, migration, commit or remote row
was changed. D1 access was SELECT-only. The only file written is this one.

Evidence tags used throughout:

- `[VERIFIED <file:line | command + output>]` — directly observed in this audit.
- `[INFERRED <reason>]` — follows from verified facts but was not directly observed.
- `[UNKNOWN <what is needed>]` — not determinable from the repo or the read-only surface.

---

## 1. Executive summary

The runtime core is real and mostly sound: a modular Worker, D1 as the only task-state store, a
bounded scheduler, lease recovery, hashed sessions, hashed device tokens, a working egress
sanitizer, and 461 passing unit assertions across 19 suites plus two gate suites. `tsc` is clean
on both projects. The failures are not in the plumbing; they are in what has been *loaded into
production*, what has *not been built*, and three specific logic gaps that mis-report or
mis-deliver.

Top five risks:

1. **Production D1 is contaminated with test fixtures, and those fixtures are newest-first in
   prompt retrieval.** 15 `mem_seed_*` rows and `mem_m12_priv` are live (19 memories total, 3
   real). 43 desktop devices exist, 40 unrevoked. `settings` holds two `album_test_*` keys.
2. **Production exposes arbitrary-SQL execution behind a bearer that the test suites mint
   themselves**, and `/api/v1/internal/*` is excluded from the global auth middleware.
3. **The egress guard is bypassable** by a typographic apostrophe; a real reply claiming a
   deletion that never happened was delivered to the owner on 2026-11-08 14:34 UTC.
4. **102 pending reminders belong to archived tasks** and the scheduler only suppresses `done`
   and `dismissed`; they fire between 2026-11-09 and 2026-11-21 and consume the 3/day cap.
5. **The entire AI-quality layer from the last build prompt is absent**: no grounding verifier,
   no style linter, no `turn_log`, no `/why`, no eval set, no test CI, and the Daemon persona in
   the spec was never written into `prompts.ts`.

Nothing in the audit indicates data loss or credential compromise. Reliability is the weakest
area, observability second.

### C. Guards

`worker/telegram.ts:188-217` runs every outbound send through `sanitizeOutboundMessage`, which
(a) drops anything that looks like a JSON payload or contains `_mock`/`reply_text`/`"intent"`,
replacing it with "AI is temporarily offline…"; then (b) applies `guardReply(text, ctx)`.

`guardReply` [VERIFIED `egressGuard.ts:52-83`]: if no `ctx`, return unchanged (this is how
reminders/digests escape the guard — correct per ADR-049); if the text equals a committed
`actionResults` entry, allow; if any of 7 regexes match, replace with the first committed result
or `"No action taken."`.

What it actually blocks: leading first-person past-tense action verbs, "Got it, …", "all/both
those tasks have been …", "successfully <verb>", and "closing/closed windows".

Known bypasses:
- Unicode apostrophe (`’`) — verified bypass, delivered in production (F3).
- Contraction-free future claims: `"I’ll call you Yogi…"` was delivered [VERIFIED chat
  14:30:21Z]; "I will remove…" is not matched at all.
- Passive/agentless claims: "The task was removed for you." (no `\bI\b`).
- Claims after a leading emoji or quote character — `^`-anchored patterns only.
- Anything sent with `options.egress` omitted. Only one send site passes it
  [VERIFIED `telegramConversation.ts:229`]; broadcasts, briefings and `/commands` replies go
  unguarded by design.

False-positive risk: the patterns are anchored or `\b`-scoped, so mid-sentence factual uses
("the report completed early", "saved you a seat") do not trip them. Reminders and digests are
untouched because no EgressContext is passed. Risk of the `sanitizeOutboundMessage` JSON check
is higher: any reply that literally starts with `{` and ends with `}` is replaced, and so is any
reply containing the substring `reply_text` or `"intent"` — a user asking "what does reply_text
mean" would be answered with the offline notice [INFERRED from `telegram.ts:196-212`].

`forget` handler [VERIFIED `worker/memoryActions.ts:175-290`]: tokenises the query (stopwords,
≤8 tokens), `LIKE`-matches live rows, never deletes when >1 match (lists up to 5), soft-deletes
via `deleted_at`, enqueues one mirror delete job per committed id, falls back to removing
matching sentences from `settings.about_me_summary`. Reply text is generated from
`deletedIds.length`. Pre-routing happens before the LLM
[VERIFIED `telegramConversation.ts:758-790`], so "forget X" cannot be turned into a remember
proposal. Proposal rules: AI may only create `task_proposals`/`memory_proposals` rows; commit
requires a callback. This part is sound and is the best-implemented guard in the system.

Gap: there is no grounding verifier and no style linter. Every fact in a reply is unchecked
against context. Section J shows three invented/unsupported statements.

### F. Reliability

Cron: one trigger, `* * * * *` [VERIFIED `wrangler.jsonc:34-37`] → 1,440 invocations/day. Each
invocation runs `sweepStaleChatMessages`, three retention DELETEs, briefing check, mirror
reconcile (self-limited to once/24 h), heartbeat (every 15 min), Gmail ingestion, then
`runScheduler` [VERIFIED `index.ts:1800-1832`]. Scheduler: bounded batch `min(max(1,n),5)` with
default 3 [VERIFIED `scheduler.ts:26-28,120`]; claim is a single
`UPDATE … WHERE id IN (SELECT … LIMIT ?) RETURNING` [VERIFIED `:207-236`]; lease 30 s with
expiry recovery that releases cap reservations [VERIFIED `:141-175`]; retries 3 transient /
1 unknown, then `dead`; 429 honours `retry-after` capped at 10 s [VERIFIED `:499`].

Correctness problems in that loop: archived tasks are not suppressed (F4); first-fire reminders
are capped at 3/day (F5); the retention DELETE names a table that does not exist (F10).

Failure modes:

  [VERIFIED `scheduler.ts:330-380, 480-520`]; unknown sends are never retried twice, which
  implements "never promise exactly-once".
- Groq down → circuit cooldown + next candidate; all down → typed error, chat falls back to a
  code template. Briefings and digests are code-built, so they survive provider outage
  [VERIFIED `briefings.ts` contains no model call].
- D1 down → most handlers `.catch(() => {})` and degrade to empty results; the webhook still

  outages from Telegram.

- **Duplicate routes.** `/api/v1/today`, `/tomorrow`, `/export`, `/auth/pair` are implemented

  [VERIFIED `:74-77`], so apiRouter's copy at `:165` is dead.

  `+05:30` and UTC getters — correct. Re-implementations: `attention.ts:54-58` (manual offset),
  `callbacks.ts:320-329` (manual offset then `toISOString().slice(0,10)`),
  `telegramAssistant.ts:649,681,770` (`now + 5.5h` inline), `telegramConversation.ts:391,1310,
  1398` (same). UTC-date bugs: `briefings.ts:236` counts "completed today" from the UTC date;
  `captureEngine.ts:141` uses the UTC date as "today"; `telegramConversation.ts:194` likewise.
  At 20:30 IST these happen to be the same day; between 00:00 and 05:29 IST they are not.
  The "Monday vs Sun 8 Nov" report is **not** a bug: 2026-11-08 *is* Sunday [VERIFIED node], the
  evening briefing said "Tomorrow (Monday)" with no date, and `formatConfirmationDate` said
  "Sun 8 Nov". The fix is to print dates alongside weekdays, not to correct arithmetic.
- **Intent routing order** [VERIFIED `telegramConversation.ts:758-800, 940-1110`]:
  deterministic pre-router (forget/remember) → LLM classifier → regex overrides
  (leaving-college, on-the-way-home, weather, time-only reminders) → intent switch. Order is
  stable and sensible; the risk is that regex overrides can overwrite a good classifier result
  (`result.intent = "schedule_exception"` at `:991` does exactly that).
- **Compound messages:** split into ≤3 clauses at `deterministicParser.ts:385-399`, then handled
  sequentially with one reply per clause; `:1492` appends the chat part. Works for the two
  cases in `unit_input` (47 assertions) but has no cross-clause dependency handling ("cancel the
  first one" cannot refer to the second clause) [INFERRED].
- **Language:** no language detector; language handling is (a) prompt instruction, (b) regex
  lexicons (`dateLexicon.ts`, `captureEngine.ts:37-60`) and (c) two `ippudu` checks
